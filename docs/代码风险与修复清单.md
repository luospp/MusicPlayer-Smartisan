最需要优先处理的四件事：

1. `MusicActivity` 在 Android 8~12 上申请了一个**未在 Manifest 声明**的权限，首次启动必然被拒，扫描流程走不下去（P0-04）。
2. 通知栏与倒计时使用的自定义广播 action 是裸字符串 `"MUSIC"`，注册时未加 `RECEIVER_NOT_EXPORTED`，**任意第三方 App 都能控制播放、篡改收藏、停掉服务**（P0-08）。这也是升级 targetSdk 34 的直接拦路虎。
3. `MainActivity` 把 Service Binder 放在 `companion object` 静态字段里，且 `isPlayFlag` 永不复位，**服务被系统回收后回到主页必崩**（P0-01）。
4. QQ 音乐歌词刷新定时器的时间单位写成了 `MICROSECONDS`，实际是 **1.6 毫秒一次**，每秒约 600 次主线程回调（P0-06）。

## 二、P0 级问题

### P0-01 静态 Binder + 状态标记不复位导致必崩

位置：`app/src/main/java/com/yibao/music/activity/MainActivity.kt:539-548`、`761-766`

现象：播放中切到后台，系统回收 `MusicPlayService` 后回到 App，`onResume()` 崩溃。

原因：`AudioServiceConnection.onServiceConnected` 把 Binder 写进 `companion object` 的静态字段 `audioBinder`，`onServiceDisconnected` 只把它置 null，但静态的 `isPlayFlag` 仍是 `true`；`onResume()` 里 `if (isPlayFlag) { setMusicInfo(audioBinder!!.musicBean) }` 直接 `!!` 解引用。另外静态持有 Service 的内部类 Binder，等于**长期持有整个 Service 及其 Context**，是确定的内存泄漏（LeakCanary 在 debug 包会报）。

修复：

1. 去掉 `companion object` 里的 `audioBinder`，改为 Activity 实例字段，或引入一个 `PlaybackViewModel` + `StateFlow<PlaybackState>` 承载播放状态。
2. `onServiceDisconnected` 里同步把 `isPlayFlag` 置 false，并广播一次「服务已断开」事件让所有页面降级到未绑定 UI。
3. 所有 `audioBinder!!` 改为 `audioBinder?.let { }`，未绑定时走 `SnakbarUtil.firstPlayMusic`。全项目共 **46 处** `audioBinder!!`（`MainActivity.kt` 27 处、`SearchActivity.kt` 19 处）；Java 侧 `BasePlayActivity` + `PlayActivity` 另有 **43 处** `audioBinder.xxx()` 直接调用，其中只有 9 处套了 `audioBinder != null` 判断，其余 34 处均为裸解引用。

### P0-02 MediaPlayer 全流程无空判断

位置：`service/MusicPlayService.java:176-178`、`242`、`247`、`315`、`320`、`330-331`、`338`、`346`

现象：切到一首已删除/损坏/无权限的音频时，服务进程崩溃；或者播放器静默停住不再自动切歌。

原因：`MediaPlayer.create()` 失败时返回 **null**，紧接着 `mediaPlayer.setOnPreparedListener(this)` 就 NPE。`getProgress()`、`getDuration()`、`isPlaying()`、`start()`、`pause()`、`seekTo()`、`setPlaybackParams()` 全部无判空。另外**没有注册 `setOnErrorListener`**，所以解码失败时既不会自动跳下一首，也不会给用户任何提示。

修复：

```java
mediaPlayer = MediaPlayer.create(this, getSongFileUri());
if (mediaPlayer == null) {
    LogUtil.e(TAG, "create failed: " + getSongFileUri());
    skipToNextOnError();   // 记录失败次数，连续失败 N 次后停止并提示
    return;
}
mediaPlayer.setOnErrorListener((mp, what, extra) -> { skipToNextOnError(); return true; });
```

所有对外方法统一加 `if (mediaPlayer == null) return 默认值;`。中期建议直接换 Media3 ExoPlayer（见 P2-14）。

### P0-03 `onStartCommand` 未处理 null Intent 与越界索引

位置：`service/MusicPlayService.java:112-146`

现象：系统重建服务或异常启动时崩溃。

原因：`intent.getIntExtra(...)` 未判空（`START_NOT_STICKY` 下概率低但非零）；`mMusicDataList.get(playPosition)` 的钳制逻辑写在 `play()` 内部，`onStartCommand` 里 `play()` 之后又直接用 `playPosition` 取元素，一旦列表被重新查询成更短的列表就越界。`playPre()` / `playNext()` / `autoPlayNext()` 在列表为空时调用 `new Random().nextInt(0)` 会抛 `IllegalArgumentException`。

修复：`onStartCommand` 开头 `if (intent == null) return START_NOT_STICKY;`；把索引钳制抽成 `private int clamp(int pos)`，所有取元素前统一调用；随机播放改用「排除当前曲目」的算法（见 P1-14）。

### P0-04 申请了未声明的权限，Android 8~12 首启卡死

位置：`activity/MusicActivity.kt:54-75`，`AndroidManifest.xml:8-33`

现象：在 Android 8.0~12 的设备上首次启动，弹一次「请打允许存储的读写权限」对话框后无法继续，永远扫不到歌。

原因：`initPermission()` 在 `checkAndroidVersionS()`（实为 API ≥ 33）为 false 时申请 `Manifest.permission.WRITE_EXTERNAL_STORAGE`，但 **Manifest 里根本没有声明 `WRITE_EXTERNAL_STORAGE`**，只有 `maxSdkVersion="32"` 的 `READ_EXTERNAL_STORAGE`。系统对未声明的权限直接返回 denied 且不弹框，于是走 `againPermission()` 死路。Android 13+ 走 `READ_MEDIA_AUDIO` 分支才正常。

修复：

```kotlin
private fun initPermission() {
    val permission = if (Build.VERSION.SDK_INT >= 33) {
        Manifest.permission.READ_MEDIA_AUDIO
    } else {
        Manifest.permission.READ_EXTERNAL_STORAGE   // Manifest 已声明 maxSdkVersion=32
    }
    requestPermissionLauncher.launch(permission)
}
```

同时把「拒绝后重试一次」的逻辑改为 `shouldShowRequestPermissionRationale` 判断，避免无意义的二次弹窗。

### P0-05 Retrofit `@Headers` 格式非法

位置：`network/ApiService.java:63`，`util/Api.java:19`

现象：调用 `getSingerImg()` 时抛 `IllegalArgumentException: @Headers value must be in the form [name]: [value]`。

原因：`Api.HEADER_USER_AGENT` 的值是 `"Mozilla/5.0 (Macintosh; ...)"`，**没有 `名字: 值` 的冒号分隔**，Retrofit 在解析注解时直接抛异常，而且异常发生在动态代理调用点，不会被 RxJava 的 `onError` 捕获，会直接崩到调用方。

当前影响：`getArtistImg()` 的唯一调用点已被注释（`view/music/DetailsView.java:215`），所以是**未引爆的地雷**。

修复：改为 `"User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ..."`，或删掉 `getSingerImg` 与 `getArtistImg` 这条已停用的网易云链路。

### P0-06 歌词定时器时间单位错误（1.6 毫秒）

位置：`activity/MainActivity.kt:432-459`

现象：切到 QQ 风格控制条后，手机明显发热、掉帧、耗电异常。

原因：`Observable.interval(1600, TimeUnit.MICROSECONDS)` 是 **1600 微秒 = 1.6 毫秒**，意图显然是 1600 毫秒。每秒约 600 次回调，每次都执行 `audioBinder!!.progress`、列表读写、`LogUtil.d`（内含 `Thread.currentThread().getStackTrace()`）和 `qqControlBar.setPagerData()`。

修复：改成 `TimeUnit.MILLISECONDS`；同时把间隔调到 200~300 ms（歌词时间戳精度是毫秒级，1.6 秒的刷新粒度本身也太粗）；删掉循环体内的 `LogUtil.d`。

### P0-07 进程重建后 Dialog 静态参数丢失导致崩溃

位置：`fragment/dialogfrag/MoreMenuBottomDialog.kt:95-113`，同类问题见 `ScannerConfigDialog.kt`（companion 里的 `lateinit var mListener`）、`PlayListFragment.java:50-55`（`static String mSongName` / `static ArrayList mArrayLisOpenDetail` / `static boolean isFromPlayListActivity`）

现象：弹出「更多菜单」后切后台被回收，回来即崩；或者两个 `PlayListFragment` 实例互相串数据（Tab 里的歌单页标题/工具栏可见性被「加到播放列表」流程改掉）。

原因：用 `companion object` 静态字段代替 `arguments` 传参。框架重建 DialogFragment 时不会走 `newInstance`，静态字段为 null，`mMusicBean!!` 立即 NPE。`ScannerConfigDialog` 的静态 `lateinit` 还会抛 `UninitializedPropertyAccessException`。

修复：全部改为 `arguments` + `Parcelable`（`MusicBean` 已实现 Parcelable），监听器改为 `FragmentResult` API 或 `requireParentFragment()` 接口查找。`PlayListFragment` 的三个 static 字段改为实例字段 + arguments。

### P0-08 自定义广播可被任意 App 伪造（安全漏洞）

位置：`service/MusicPlayService.java:456-463`（`initNotifyBroadcast`）、`service/CountdownService.java:56-60`、`base/BasePlayActivity.java:158-164`、`util/Constant.java:20`

现象：设备上任意第三方 App 执行 `sendBroadcast(Intent("MUSIC").putExtra("notify_btn_id", 4))` 即可**暂停播放并关闭通知**；传 `0` 可**篡改当前歌曲的收藏状态并写库**；传 `1`/`3` 可任意切歌。

原因：

1. action 是裸字符串 `"MUSIC"`，无包名前缀，极易与其他 App 冲突或被定向伪造。
2. `registerReceiver(receiver, filter)` 未指定 `RECEIVER_NOT_EXPORTED`，在 API ≤ 33 上默认导出。
3. `PendingIntent.getBroadcast` 使用**隐式 Intent**（未 `setPackage`），其他 App 的接收器也能收到，存在信息泄露与劫持面。
4. 接收器内部没有任何来源校验。

附带影响：**升级 targetSdk 到 34 后，`registerReceiver` 不传导出标志会直接抛 `SecurityException`**，三处注册全部受影响，这是升级的硬性阻塞项。

修复：

```java
// 1. action 加包名前缀
public final static String ACTION_MUSIC = "com.yibao.music.action.MUSIC_CONTROL";

// 2. 注册为不导出（ContextCompat 兼容全版本）
ContextCompat.registerReceiver(this, mMusicReceiver, filter, ContextCompat.RECEIVER_NOT_EXPORTED);

// 3. PendingIntent 用显式 Intent
Intent play = new Intent(activity, MusicPlayService.MediaActionReceiver.class);
//   或至少 intent.setPackage(activity.getPackageName());
```

更彻底的方案：废弃广播，改用 `MediaSessionCompat.Callback` 或 `Media3 MediaSession` 统一承接通知栏/锁屏/蓝牙/耳机线控，通知按钮直接由 `MediaStyle` + `MediaSession` 处理（见 P1-01）。

### P0-09 明文流量全开 + 无网络安全配置

位置：`AndroidManifest.xml:36`（`android:usesCleartextTraffic="true"`）、`network/RetrofitHelper.java`、`util/Api.java`

现象：全部 HTTP 明文传输，中间人可篡改返回内容（歌词、专辑图、JSON）。

原因：Manifest 全局放开明文；`Api.java` 里 1835 条硬编码图片直链中 **1814 条是 `http://`**；专辑图 base 也是 `http://y.gtimg.cn/...`。项目没有 `network_security_config.xml`。

修复：

1. `usesCleartextTraffic` 改为 `false`。
2. 新增 `res/xml/network_security_config.xml`，如确有个别域名必须明文，用 `<domain-config cleartextTrafficPermitted="true">` 精确白名单，而不是全局放开。
3. 专辑图、歌词接口统一切 HTTPS（QQ 音乐的 `c.y.qq.com`、`y.gtimg.cn` 均支持 HTTPS）。
4. `Api.java` 整个删除（见 P0-12）。

### P0-10 权限声明严重超范围（合规/上架风险）

位置：`AndroidManifest.xml:8-33`

现象：Google Play、国内各应用商店的权限审查会被直接拦下；用户看到「精确位置」「后台位置」「相机」「读取手机状态」会强烈质疑。

超范围清单（对一个本地音乐播放器而言）：

| 权限 | 是否必要 | 说明 |
|---|---|---|
| `ACCESS_FINE_LOCATION` | 否 | 全项目无任何位置 API 调用 |
| `ACCESS_BACKGROUND_LOCATION` | 否 | 声明后台定位，Google Play 需提交视频演示 + 隐私政策，几乎必被拒 |
| `ACCESS_COARSE_LOCATION` | 否 | 同上 |
| `READ_PHONE_STATE` | 否 | 仅百度统计 SDK 可能使用，属敏感权限 |
| `CAMERA` + `uses-feature camera` | 弱 | 仅「拍照设头像」彩蛋功能 |
| `BLUETOOTH` / `BLUETOOTH_ADMIN` | 否 | 未做任何蓝牙 API 调用；耳机线控走 `ACTION_AUDIO_BECOMING_NOISY` 与 MediaSession，不需要 |
| `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` | 弱 | 视频权限完全无用；图片权限仅头像彩蛋 |
| `ACCESS_WIFI_STATE` | 否 | `NetworkUtil` 只用 `ConnectivityManager` |

并且 `MainActivity.kt:712-726` 的 `initLocationPermission()` **在主页启动时无条件申请 `ACCESS_FINE_LOCATION`，被拒后还会再申请一次**。

修复：删除上表中所有「否」项；`initLocationPermission()` 整段删除；头像功能改为 `ACTION_PICK` / `PhotoPicker`（无需任何权限），拍照改为可选的 `CAMERA` 且只在用户主动点击时才申请；Manifest 补齐 `FOREGROUND_SERVICE_MEDIA_PLAYBACK`（配合 P1-01）。

### P0-11 `allowBackup` 开启且备份规则为空

位置：`AndroidManifest.xml:38-39`、`res/xml/data_extraction_rules.xml`（全文都是注释模板）

现象：`favorite-db` 数据库、`music_config` SharedPreferences（含播放位置、播放模式、语言、扫描配置）会被完整云备份 / 设备迁移，`adb backup` 在旧系统上也可导出。lint 已报 `DataExtractionRules`。

修复：要么 `allowBackup="false"`，要么在 `data_extraction_rules.xml` 与 `full_backup_content.xml` 里明确 `<exclude domain="database" path="favorite-db"/>` 等规则。本项目数据都可从 MediaStore 重建，建议直接关掉备份。

### P0-12 `Api.java` 硬编码 1835 条第三方图片直链

位置：`util/Api.java`（1920 行，占全项目代码量的 7%）

风险：

1. **肖像权 / 版权**：数组内容是大量真人明星照片（注释里直接写着艺人姓名），来源是堆糖、百度图片、新浪图床、Photobucket、B 站等第三方站点，无授权、无出处。
2. **盗链**：直接引用他人图床，随时 403，且给对方站点带来流量成本。
3. **链接腐烂**：这些 URL 采集于 2015~2017 年，现在绝大多数已失效，实际显示的是占位图。
4. **明文 HTTP**：1814 条 `http://`，与 P0-09 叠加。
5. **隐藏入口**：长按「关于」页头像 → `RelaxDialogFragment` → 随机展示这些图片；同一个 `SplashPagerAdapter` 还是启动页背景，即**每次冷启动都会随机加载一张**。

修复：删除 `Api.picUrlArr` / `picUrlArr1` 与 `SplashPagerAdapter`、`RelaxDialogFragment`、`RandomUtil.getRandomUrl`。启动页改用本地 drawable 或纯色 + Logo；如确实想要网络壁纸，改为自有服务端下发 + HTTPS + 明确授权来源，并加开关与缓存。这一项同时能减掉约 1900 行代码和一部分 APK 体积。

### P0-13 歌词解析未捕获 `NumberFormatException`

位置：`util/LyricsUtil.java:159-181`（`parseTime`）

现象：下载到的 LRC 文件里只要有一行时间戳格式异常（例如 `[00:12.34.56]`、`[ab:cd]`、`[]`），解析时抛未捕获异常，播放页崩溃。

原因：`arr[0].substring(1)` 在片段为空时抛 `StringIndexOutOfBoundsException`；`Integer.parseInt(min)` / `Float.parseFloat(sec)` 抛 `NumberFormatException`；外层只 catch 了 `IOException`。歌词来自公网，属于**不可信输入**。

修复：`parseTime` 整体包 try/catch，失败返回 0 并跳过该行；用正则 `^\[(\d{1,3}):(\d{1,2})(?:[.:](\d{1,3}))?]` 做严格匹配后再解析。

### P0-14 恢复收藏时字符串越界

位置：`service/LoadMusicDataService.java:112-113`、`fragment/AboutFragment.kt:186-187`

现象：点击「恢复收藏歌曲」或扫描后自动恢复时崩溃。

原因：`s.substring(0, s.lastIndexOf("T"))`，当 favorite.txt 中某行不含字符 `T` 时 `lastIndexOf` 返回 -1，`substring(0, -1)` 抛 `StringIndexOutOfBoundsException`。歌名是任意用户数据，中文歌名不含 `T` 极其常见；文件格式一旦损坏（例如被 `againWrite` 写成空行）就会触发。`AboutFragment` 里这段跑在**主线程**的点击回调中。

修复：改用结构化存储（JSON / 单独一列 / Room 表），彻底放弃「歌名 + T + 时间」的字符串拼接格式；过渡期至少加 `val idx = s.lastIndexOf('T'); if (idx <= 0) continue`。

## 三、P1 级问题（功能实际不正确）

### P1-01 播放服务不是前台服务，通知实现方式过时

位置：`service/MusicPlayService.java`（全类无 `startForeground`）、`manager/MusicNotifyManager.kt`

问题：

1. 服务只用 `startService` + `bindService` 启动，**从未调用 `startForeground()`**。Android 8+ 上后台无法 `startService`（抛 `IllegalStateException`），且进程进入 cached 状态后随时被杀，「后台播放」实际不可靠。
2. 通知用 `setCustomContentView` + `RemoteViews` 自绘，**没有使用 `MediaStyle`**。后果：Android 13+ 的系统媒体控制中心不认它、锁屏没有标准媒体卡片、没有 `MediaSession` token 关联、通知按钮不跟随系统媒体路由。
3. 通知渠道 `IMPORTANCE_HIGH` + `PRIORITY_HIGH`，媒体通知应当是 `IMPORTANCE_LOW`（无声、不横幅）。渠道名硬编码 `"artist_music"`，未走 string 资源，无法本地化。
4. `hide()` 调的是 `mNotifyManager.cancelAll()`，会**连带清掉本 App 的所有其他通知**。
5. `showNotification()` 每次都 `new MusicNotifyManager(...)`，无复用。

修复：

```java
// onCreate 或首次 play() 时
NotificationCompat.Builder b = new NotificationCompat.Builder(this, CHANNEL_ID)
        .setSmallIcon(R.drawable.noalbumcover_120)
        .setContentTitle(title).setContentText(artist)
        .setLargeIcon(cover)
        .setStyle(new androidx.media.app.NotificationCompat.MediaStyle()
                .setMediaSession(mSessionManager.getSessionToken())
                .setShowActionsInCompactView(0, 1, 2))
        .addAction(prev).addAction(playPause).addAction(next)
        .setVisibility(NotificationCompat.VISIBILITY_PUBLIC)
        .setOngoing(isPlaying).setOnlyAlertOnce(true);
startForeground(NOTIFY_ID, b.build());
```

配套：Manifest 加 `android:foregroundServiceType="mediaPlayback"` 与 `FOREGROUND_SERVICE_MEDIA_PLAYBACK` 权限；渠道重要度降为 `IMPORTANCE_LOW`；`hide()` 改为 `cancel(NOTIFY_ID)`。中期建议整体迁到 Media3 `MediaSessionService`，可一次性解决 P0-02、P0-08、P1-01、P1-02、P2-14。

### P1-02 MediaSession 上报的播放位置是「列表下标」

位置：`manager/MediaSessionManager.java:60-66`

```java
stateBuilder.setState(state, mAudioBinder.getProgress(), 1.0f);
```

### P1-03 MediaSession 封面解码在主线程且未压缩

位置：`manager/MediaSessionManager.java:97-105`

现象：切歌瞬间卡顿；封面较大时可能触发 `TransactionTooLargeException`（Binder 单次事务上限约 1 MB）导致系统进程侧异常。

### P1-04 通知栏封面图的返回逻辑完全写反

位置：`manager/MusicNotifyManager.kt:139-142`

```kotlin
private fun createCover(path: String): Bitmap {
    BitmapFactory.decodeFile(path) ?: return BitmapFactory.decodeFile(path)
    return BitmapFactory.decodeResource(activity.resources, R.drawable.noalbumcover_220)
}
```

现象：通知栏**永远显示默认占位图**，从不显示真实专辑封面。

原因：解码成功时（非 null）`?:` 不触发，函数往下走返回占位图；解码失败时（null）执行 `return BitmapFactory.decodeFile(path)`，返回的还是 null——由于 Java 互操作的平台类型，Kotlin 不报错，null 被传给 `setImageViewBitmap`。逻辑与意图完全相反，而且白白解码了两次文件。

修复：

```kotlin
private fun createCover(path: String): Bitmap? =
    BitmapFactory.decodeFile(path)?.takeIf { it.byteCount <= MAX_NOTIFY_BITMAP_BYTES }
        ?: BitmapFactory.decodeResource(activity.resources, R.drawable.noalbumcover_220)
```

### P1-05 Android 8~11 通知按钮点一次就失效

### P1-06 双 Retrofit 单例共用一个 baseUrl，歌手图接口必然打错域名

### P1-07 专辑图/歌手图缓存查询与写入路径不一致，缓存永不命中

位置：`util/ImageUitl.java:158-166`（写入）、`util/FileUtil.java:57-66`（查询）、`util/StringUtil.java:66-71`

现象：每次滚动到专辑墙/详情页都会重新发起网络请求下载专辑图，流量与卡顿明显；Android 10+ 上尤其严重。

原因：

1. 写入侧在 `checkAndroidVersionQ()` 为真时**无论 imageType 是 1/2/3 都写到 `FileUtil.createFile(context, fileName, "songAlbum")`**。
2. 查询侧 `albumFileExists(imageType, ...)` 对 imageType 2/3 检查的是 `/sdcard/smartisan/music/artistImage/` 和 `/sdcard/smartisan/music/album/`——这两个路径在 Android 10+ 的分区存储下**既写不进去也读不出来**（应用没有 `MANAGE_EXTERNAL_STORAGE`）。

修复：统一到一个 app 私有目录并按类型分子目录：

```java
File dir = new File(context.getExternalFilesDir(null), "images/" + imageType);
```

查询与写入共用同一个 `resolveImageFile(imageType, key)` 方法，删掉 `Constant.MUSIC_ALBUM_ROOT` / `MUSIC_ARTIST_IMG_ROOT` / `HEADER_PATH` 等所有共享存储路径常量。更省事的做法是**完全交给 Glide 的磁盘缓存**，删掉这套手写下载 + 复制逻辑（同时解决 P1-08）。

### P1-08 文件复制按固定 1024 字节整块写，图片必然损坏

位置：`util/ImageUitl.java:172-196`（`copy`）

```java
byte[] buffer = new byte[1024];
while (fileInputStream.read(buffer) > 0) {
    fileOutputStream.write(buffer);   // 忽略了实际读到的字节数
}
```

现象：保存下来的专辑图文件大小总是 1024 的整数倍，尾部是上一轮的残留数据；文件尺寸不是 1024 整数倍时图片解码失败或显示错乱。

附带问题：`fileInputStream` 从未关闭（FD 泄漏）；异常只 `printStackTrace`。

修复：

```java
try (FileInputStream in = new FileInputStream(source);
     FileOutputStream out = new FileOutputStream(target)) {
    byte[] buffer = new byte[8192];
    int len;
    while ((len = in.read(buffer)) > 0) out.write(buffer, 0, len);
}
```

或直接删掉这段，改用 Glide 的 `downloadOnly` + 缓存目录（推荐）。

### P1-09 下载专辑图重复请求两次网络

现象：每张图产生两次完整下载，流量翻倍、耗时翻倍。

### P1-10 收藏备份/恢复在 Android 10+ 完全失效

位置：`util/ReadFavoriteFileUtil.java:32`、`util/FileUtil.java:35-37`、`fragment/AboutFragment.kt:180-230`

现象：Android 10 及以上点「备份收藏歌曲」会提示成功，但文件其实没写出去；「恢复收藏歌曲」永远提示找不到文件。

原因：`FAVORITE_FILE` 指向 `/sdcard/smartisan/music/favorite.txt`，父目录从未创建，且分区存储下应用无权写入共享存储根目录。`writeFile` 里 `createNewFile()` 抛 `IOException` 被 catch 后仅 `printStackTrace`，`backupsFavoriteList()` 无论如何都会 `showFavoriteListBackupsDown`（「备份完成」）——**假成功提示**。

附带问题：`againWrite()` 在 `list` 为空时先 `new FileOutputStream(file)` 再判断 `!file.exists()`，顺序颠倒；`deleteFavorite` 的 `stringToSet(str)` 用 `text.contains(str)` 做匹配，**歌名是另一首歌名的子串时会误删**（例如「晴天」会连带删掉「晴天的日子」）。

修复：备份文件改到 `context.getExternalFilesDir("backup")` 或 `filesDir`；格式改 JSON（`[{"title":"...","time":"..."}]`）；用精确匹配代替 `contains`；写失败必须回传 false 并提示用户。如果要支持「卸载重装后恢复」，应改用系统备份（`allowBackup` + `BackupAgent`）或 SAF 让用户显式选择导出位置。

### P1-11 删除歌词在 Android 10+ 无效

位置：`util/LyricsUtil.java:44-53`（`deleteCurrentLyric`）vs `util/FileUtil.java:143-153`（`getLyricsFile`）

现象：播放页点「删除歌词」，提示都没有，歌词依然存在。

原因：`getLyricsFile` 在 Q+ 返回 app 私有目录 `files/lyrics/歌名$$歌手.lrc`，而 `deleteCurrentLyric` 硬编码用 `Constant.MUSIC_LYRICS_ROOT`（`/sdcard/smartisan/music/lyrics/`）拼路径，删的是一个不存在的文件。

修复：`deleteCurrentLyric` 改为 `FileUtil.getLyricsFile(songName, artist).delete()`，删除结果回传并提示。

### P1-12 歌词文件是追加写入，重复下载会叠加内容

位置：`util/DownloadLyricsUtil.java:44-52`

现象：同一首歌重新下载歌词后，LRC 文件里出现两份甚至多份时间轴，滚动歌词错乱、行数翻倍。

原因：`new RandomAccessFile(file, "rwd"); raf.seek(file.length()); raf.write(...)` 是**追加**语义。`raf.close()` 不在 finally 中，异常时句柄泄漏。`strContent.getBytes()` 用平台默认字符集而非 UTF-8。

修复：

```java
try (OutputStream os = new FileOutputStream(file, false)) {   // 覆盖写

}
```

另外 `FileUtil.getLyricsFile` 在 pre-Q 分支拼路径时**漏了 `File.separator`**（`new File(dir.getAbsolutePath() + lyricsName)`），会得到 `.../lyrics歌名$$歌手.lrc` 这种畸形路径，一并修掉。

### P1-13 定时关闭不是前台服务，锁屏后可能静默失效

位置：`service/CountdownService.java`、`fragment/dialogfrag/CountdownBottomSheetDialog.java:98-110`

现象：设置了 2 小时定时，实际可能 20 分钟后进程被杀，音乐一直放一整晚。

原因：`CountdownService` 是普通 Service（无 `startForeground`），进程进入 cached 状态后随时可被回收，`CountDownTimer` 随之消失。`onStartCommand` 里 `intent.getLongExtra` 未判空；重复设置定时时**旧 timer 未 cancel** 就 new 一个，会出现两个倒计时并发。倒计时到点用隐式广播 `sendBroadcast(new Intent("MUSIC"))` 通知暂停，叠加 P0-08 的问题。

修复：改用 `AlarmManager.setExactAndAllowWhileIdle` + `BroadcastReceiver`，或把倒计时并入播放服务（前台服务）用 `SystemClock.elapsedRealtime()` 计算；`onStartCommand` 先 `if (mMusicTimer != null) mMusicTimer.cancel()`；到点直接调用 Binder 的 `pause()` 而不是发广播。UI 上补一句「定时依赖播放服务存活」的说明，或在前台通知里显示剩余时间。

### P1-14 随机播放可能连续重复同一首，且每次 new Random

位置：`service/MusicPlayService.java:270-302`

原因：`new Random().nextInt(size)` 每次新建实例（种子来自 `System.nanoTime()`，高频调用时可能相近），且不排除当前曲目，单曲列表时 `nextInt(1)` 恒为 0。

修复：持有一个 `Random` 实例；随机模式改为「洗牌队列」算法——生成 0..n-1 的乱序列表，按序消费，消费完再重排，可保证不重复且全覆盖。

### P1-15 「加到播放列表」传参 key 不一致，参数永远为 null

## 四、P2 级问题（性能 / 内存 / 稳定性）

### P2-01 大量数据库操作跑在主线程

| 位置 | 操作 |
|---|---|
| `viewmodel/SongViewModel.kt:19-40` | 四种排序的整表查询 |

### P2-02 `PlayListViewModel` / `SearchViewModel` 被直接 new，ViewModel 形同虚设

位置：`fragment/PlayListFragment.java:56`（`private final PlayListViewModel mViewModel = new PlayListViewModel();`）、`activity/SearchLyricsActivity.kt:26`

后果：`onCleared()` 永不调用，`viewModelScope` 里的协程与 Rx 订阅无法随生命周期取消（泄漏）；配置变更（分屏、字号变化）后状态不保留；同一页面重复创建实例。

修复：改为 `by viewModels()` / `ViewModelProvider(this)[...]`（项目里 `BaseBindingActivity.gets()`、`BaseBindingFragment.gets()` 已经封装好了，直接用）。

### P2-03 `ThreadPoolProxyFactory.newInstance()` 每次调用都新建线程池

位置：`util/ThreadPoolProxyFactory.java:29-31`、`33-49`

现象：每次收藏/取消收藏、每次清理歌词都会新建一个核心线程数为 CPU+1 的 `ThreadPoolExecutor`，且**从不 shutdown**，线程持续累积。

原因：`newInstance()` 是 `return new ThreadPoolProxyFactory()`，所谓的双重检查锁只保护单个实例内部，跨调用完全无效。`mExecutor` 是实例字段而非静态字段。

附带问题：`LinkedBlockingDeque` 无界 → `MAXIMUM_POOL_SIZE` 永远用不上；`DiscardPolicy` 静默丢任务；线程名是默认的 `pool-N-thread-M`，排查困难。

修复：改为真正的单例（静态 holder 或 `object`），或直接删掉这个类改用 `kotlinx.coroutines.Dispatchers.IO` / `Executors.newSharedThreadPool` 并在 debug 下配 StrictMode。

### P2-04 Rx 轮询与订阅生命周期管理混乱

1. `base/BaseActivity.java:127-138`：`upDataPlayProgress()` 用 `Observable.interval(0, 250, MILLISECONDS)` 每 250 ms 刷一次进度。栈里每个 Activity 各有一份，`MainActivity` + `PlayActivity` 同时存在时是 8 次/秒。且回调里 `audioBinder!!.progress` 未判空。
2. `base/BasePlayActivity.java:78-89`：歌词滚动 `Observable.interval(30, MILLISECONDS)`，33 次/秒，叠加上一条。
3. `BaseActivity.subscribe()` 在 `onResume` 里注册 4 条订阅，`onPause` 里 `dispose()` + `clear()` + 置 null——`dispose()` 之后再 `clear()` 是多余操作；`mCompositeDisposable` 置 null 后，子类若在 `onPause` 之后访问会 NPE。
4. `service/MusicPlayService.java:378`：`mDisposable` 被反复赋值，**旧订阅从未 dispose**，泄漏。
5. `network/QqMusicRemote.java` 全部 `subscribe(new BaseObserver<>(){...})` 返回的 `Disposable` 被直接丢弃，`BaseObserver.onSubscribe` 里注释写着「可选择：自动添加到全局 CompositeDisposable」但没实现 → **所有网络请求都无法取消**，Activity 销毁后回调仍持有其引用。

修复：进度刷新改用 `MediaPlayer`/`ExoPlayer` 的回调或 `ValueAnimator`，避免全局轮询；所有 `subscribe` 的返回值统一进 `CompositeDisposable` 或 `viewLifecycleOwner.lifecycleScope`；`BaseObserver` 实现 `onSubscribe` 里的自动收集。

### P2-05 无限循环动画未在 View 分离时停止

位置：`view/DiscView.kt:128-140`

现象：离开播放页后唱片动画仍在跑，耗电、并持有整棵 View 树。

原因：`initAutoRotation()` 创建 `repeatCount = INFINITE` 的 `ValueAnimator`，全类没有 `onDetachedFromWindow` 去 cancel；`PlayActivity.onDestroy` 只清了 `rotateRl.clearAnimation()`（那是 View 动画，管不到 `ValueAnimator`）。另外每帧固定加 `360f / (15000 / 16f)`，**假设了 60 fps**，在 90/120 Hz 屏上唱片会转快 1.5~2 倍。

修复：

```kotlin
override fun onDetachedFromWindow() {
    autoAnimator?.cancel(); autoAnimator = null
    flingAnimator?.cancel(); flingAnimator = null
    super.onDetachedFromWindow()
}
```

旋转量改用 `it.animatedFraction * 360f` 由动画系统按真实帧率驱动，或用 `Choreographer` / `withFrameNanos`。

### P2-06 扫描本地音乐是 O(n²)，且逐条事务写库

位置：`service/LoadMusicDataService.java:57-76`、`130-141`

现象：几千首歌的库，手动「重新扫描」耗时数十秒，进度条卡顿。

原因：

1. `newList.stream().filter(item -> !oldList.contains(item))` —— `ArrayList.contains` 是 O(n)，整体 O(n²)；`MusicBean.equals` 比较 9 个字段（`model/MusicBean.java:416-448`），单次比较也不便宜。紧接着 `newList.retainAll(different)` 又是 O(n·m)。
2. `sendLoadProgress` 在循环里逐条 `mMusicDao.insertOrReplace(bean)`，**每条一个独立事务**（无 `runInTx`），SQLite 每次 fsync；同时每条都往 RxBus post 一次进度，UI 被灌满。
3. `IntentService` 自 API 30 起废弃，且后台启动受限。

修复：`oldList` 转成 `HashMap<Long, MusicBean>`（key 用 MediaStore id）做差集，O(n)；批量写用 `daoSession.runInTx { ... }` 或 `insertOrReplaceInTx(list)`；进度按 5% 或每 100 条节流上报；`IntentService` 换成 `JobIntentService` 的替代品——协程 + 普通 `Service`，或直接迁 WorkManager。

### P2-07 MediaStore 查询方式陈旧且过滤不足

位置：`util/MusicListUtil.java:47-110`

1. projection 传 `null`，取回全部列。
2. **没有 `IS_MUSIC` / `IS_ALARM` / `IS_NOTIFICATION` 过滤**，通知音、铃声、微信语音全部进库。项目用「时长 > 10800 ms、体积 > 1 MB」间接过滤，但默认两个开关都是关的。
3. `MediaStore.Audio.Media.DATA` 自 API 29 废弃，返回的路径在 Q+ 无法直接打开（播放侧已改用 `ContentUris`，但删除文件仍用 `new File(songUrl).delete()`）。
4. `cursor.getColumnIndex(...)` 可能返回 -1，随后 `cursor.getLong(-1)` 抛异常；`cursor.moveToNext()` 的返回值未检查。
5. `cursor.close()` 不在 finally 中（lint 报的 `Recycle` 就是这条）。
6. `long albumId = cursor.getInt(mAlbumId)`、`long duration = cursor.getInt(mDuration)` 用 `getInt` 读 long 列；`int addTime = (int) cursor.getLong(addDed)` 把时间戳截成 int（2038 问题）。
7. `info.setMusicQualityType(qualityType)` 与 `info.setIssueYear(issueYear)` **存的是列索引而不是列值**——`qualityType`/`issueYear` 是 `getColumnIndex` 的返回值。所以「音质类型」和「发行年份」两个字段全库都是同一个常量数字，专辑/艺术家列表里显示的年份是错的。
8. 每首歌调用 `HanziToPinyins.stringToPinyinSpecial(title)`（pinyin4j 反射 + 字典查找），几千首歌累积开销可观。

修复：显式 projection + `selection = MediaStore.Audio.Media.IS_MUSIC + "!=0"`；用 `getColumnIndexOrThrow` 或 API 29+ 的 `cursor.getString(cursor.getColumnIndexOrThrow(...))`；`try (Cursor c = ...)`；第 7 条改为 `cursor.getString(qualityType)` / `cursor.getInt(issueYear)`；首字母计算移到后台并缓存。

### P2-08 OkHttp 配置不合理

位置：`util/OkHttpUtil.java:24-40`

1. 连接/读/写超时全是 **3 秒**，弱网下歌词与专辑图必然失败（且失败后无重试）。
2. 无磁盘缓存、无 `Cache` 目录 → 每次滚动都重新下载（叠加 P1-07）。

修复：超时改为连接 10 s / 读写 20 s；加 `Cache(new File(context.getCacheDir(), "http"), 20 MB)`；锁对象改为 `OkHttpUtil.class`；日志拦截器换成 OkHttp 官方 `HttpLoggingInterceptor` 并只在 `BuildConfig.DEBUG` 下 `Level.BASIC`。

### P2-09 排序比较器违反契约，可能抛 `IllegalArgumentException`

位置：`util/MusicListUtil.java:121-135`、`viewmodel/SongViewModel.kt:50-70`

现象：大列表排序时偶发 `java.lang.IllegalArgumentException: Comparison method violates its general contract!`。

原因：`sortAbc` 对 `#` 的处理不对称——`m2.firstChar == "#"` 返回 -1，`m1.firstChar == "#"` 返回 1，但当两者都是 `#` 时先命中第一个分支返回 -1，即 `compare(a, b) == -1` 且 `compare(b, a) == -1`，违反反对称性。TimSort 会检测到并抛异常。`firstChar` 为 null 时（`HanziToPinyins` 对 null 输入返回 `(char) 0`）还会 NPE。

修复：

```kotlin
list.sortedWith(compareBy({ it.firstChar == "#" }, { it.firstChar }, { it.title }))
```

用「是否井号」作为一级 key，天然满足全序。

### P2-10 列表全部使用 `notifyDataSetChanged`，且关闭了图片缓存

位置：`base/bindings/BaseBindingAdapter.kt`（`setSelectedPosition`/`clear`/`setData`/`deleteSong`/`addData`/`setNewData` 全部 `notifyDataSetChanged`，lint 报 11 处 `NotifyDataSetChanged`）、`adapter/SongAdapter.kt:64-69`、`util/ImageUitl.java:71`、`110`

2. `onBindViewHolder` 里每行调用 `FileUtil.getAlbumUrl()` → `File.exists()`，**主线程磁盘 IO**（每行 1~2 次）。
3. `customLoadPic` / `loadPic` 都设置了 `DiskCacheStrategy.NONE`，Glide 磁盘缓存被关掉，每次重绑都要重新解码。
4. `setSelectedPosition` 用于「小喇叭」高亮，每 250 ms 的进度轮询 + 每次切歌都可能触发全表刷新。

修复：迁移到 `ListAdapter` + `DiffUtil`；`DiskCacheStrategy` 改回 `AUTOMATIC`/`RESOURCE`；封面路径解析结果缓存在 `MusicBean` 上（或直接用 `ContentUris.withAppendedId(albumArtUri, albumId)` 交给 Glide，省掉 `File.exists()`）。

### P2-11 release 包输出全量日志

### P2-13 歌词读取用静态 `BufferedReader`，多线程下会互相破坏

位置：`util/LyricsUtil.java:29`、`83-105`、`114-142`

现象：偶发歌词显示串行、`IOException: Stream closed`、或显示「歌词加载出错」。

原因：`br` 是 **static** 字段，而 `getLyricList` 会同时被主线程（`updateCurrentPlayInfo`）和 Rx 的 io 线程（`QqMusicRemote` 回调、`MainActivity.setQqPagerLyric`）调用。两个线程交叉执行 `br.readLine()` 与 `br.close()`，状态完全不可控。

修复：改为方法内局部变量 + try-with-resources：

```java
try (BufferedReader br = new BufferedReader(
        new InputStreamReader(new FileInputStream(file), StandardCharsets.UTF_8))) { ... }
```

同时把歌词解析整体移到 IO 线程，解析完再把不可变 List 抛回主线程。

### P2-14 播放内核能力不足

位置：`service/MusicPlayService.java`（`android.media.MediaPlayer`）

局限：

1. 不支持无损/高采样率格式的软解扩展、不支持流式播放、无 gapless 保证。
2. 无 `AudioAttributes`（用的是已废弃的 `STREAM_MUSIC` + `requestAudioFocus(listener, stream, durationChange)` 三参数重载，API 26 起应使用 `AudioFocusRequest`）。
3. `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK` 分支只打了一行日志，**没有实际降低音量**，导航播报时音乐会全音量盖过语音。
4. `initAudioFocus()` 只在 `start()` 里调用，`play()`（切歌）时不申请焦点。
5. 音频焦点 `AUDIOFOCUS_GAIN` 时无条件 `start()`——用户主动暂停后，若其他 App 释放焦点，音乐会**自己突然响起来**。
6. 搓碟 `setPlaybackParams` 改变 speed + pitch 后，若用户中途退出页面，倍速不会恢复（`play()` 会重建 MediaPlayer 所以最终会恢复，但中途暂停再播放时状态不确定）。
7. 没有 `WakeLock` / `WifiLock`，长列表播放中屏幕关闭后可能被系统冻结。

修复（最小改动）：改用 `AudioFocusRequest.Builder(AUDIOFOCUS_GAIN)` + `AudioAttributes(USAGE_MEDIA, CONTENT_TYPE_MUSIC)`；`CAN_DUCK` 分支实现 `setVolume(0.2f, 0.2f)` 并在 GAIN 时恢复；记录「用户主动暂停」标志，GAIN 时不自动恢复播放。

修复（推荐）：迁移到 `androidx.media3:media3-exoplayer` + `media3-session`，一次性拿到前台服务、MediaSession、通知、音频焦点、格式兼容、错误重试、`MediaBrowser` 能力，可消除 P0-02、P0-08、P1-01、P1-02、P1-03 以及本条大部分内容。

### P2-15 语言切换实现方式过时

位置：`base/BaseActivity.java:85-95`、`fragment/AboutFragment.kt:145-149`

问题：`resources.updateConfiguration(cf, dm)` 自 API 25 起废弃，在 Android 13+ 的「按应用语言」机制下行为不可靠；而且它在 `super.onCreate()` 之后、`setContentView` 之前调用，Activity 自身的资源已经解析过一轮，容易出现部分控件仍是旧语言。`switchLanguage` 只 `recreate()` 当前 Activity，栈里其他 Activity 不会刷新。

修复：改用 `AppCompatDelegate.setApplicationLocales(LocaleListCompat.forLanguageTags("en"))`（AppCompat 1.6 已具备，项目正是 1.6.1），删掉手写的 `switchLanguage()`；Manifest 加 `android:enableOnBackInvokedCallback` 与 `autoStoreLocales` 配置。lint 报的 `AppBundleLocaleChanges` 也是这条。

### P3-02 `Constant` 静态初始化依赖 Application 实例，有类加载顺序风险

位置：`util/Constant.java:174`

```java

    MusicApplication.getInstance().getExternalFilesDir("songAlbum").getAbsolutePath() + "/";
```

风险：`MusicApplication.getInstance()` 在 `appContext == null` 时会 **`new MusicApplication()`**（一个没有 `attachBaseContext` 的裸 Application 对象），此时 `getExternalFilesDir()` 返回 null → `NullPointerException` → 由于发生在静态初始化块中，会升级成 `ExceptionInInitializerError`，之后**该类永久不可用**。第三方 SDK（百度统计）的 ContentProvider 会在 `Application.onCreate()` 之前初始化，存在提前触发 `Constant` 类加载的路径。此外这一行在类加载时做磁盘 IO。
